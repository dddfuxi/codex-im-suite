# 多 Agent 协作与工作区治理实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 把 `codex-im-suite` 从少数巨型入口驱动的单体实现，渐进重构为适合多 Agent、多人和多项目协作的领域化模块单体，同时彻底隔离项目工作区、聊天附件、生成产物、运行态、记忆库和测试缓存。

**架构：** 保留现有单进程 Bridge、控制面板和 Manifest 驱动扩展模型，不直接拆微服务。先建立共享 Contract、结构化项目注册表、会话级 Scratch/Artifact 边界和兼容 Facade，再逐步拆分 Bridge Core、Feishu、Runtime、控制面板和 Skill 工作流。所有高风险动作继续由代码级权限、证据和审计门禁控制，Skill 只负责编排。

**技术栈：** TypeScript、Node.js 20+、Node Test Runner、React/Vite、.NET 9 WinForms/WebView2、PowerShell、JSON Manifest、Codex Skill、MCP。

---

## 0. 总体判断

当前项目已经具备较强测试安全网，但结构不利于并行开发：

- `apps/control-panel/Program.cs` 约 1.1 万行。
- `packages/bridge-core/src/lib/bridge/adapters/feishu-adapter.ts` 约 8900 行。
- `packages/bridge-core/src/lib/bridge/bridge-manager.ts` 约 8000 行。
- `apps/control-panel/web/src/main.tsx` 约 6600 行。
- `packages/bridge-runtime/src/main.ts` 同时承担 Composition Root、Provider、Workflow 观察和分类 Host。
- Runtime 深层导入 `claude-to-im/src/lib/...`，共享 `contracts` 尚未成为真正的跨包协议来源。
- 控制面板拥有约 110 个主命令，其中记忆、扩展、模型、发布等大量流程直接实现于 C# 宿主。
- `release` 跟踪约 300 个生成文件，增加审查和合并噪声。
- 仓库尚无 GitHub Actions、CODEOWNERS 和统一 lint/format 门禁。

已有安全资产必须保留：

- 当前工作区始终是唯一主工作区。
- 项目注册根只作为权限上界，不自动挂载。
- 其他项目只有在当前消息明确引用时才临时挂载。
- Agent Home、记忆库、运行态、上传缓存、日志和发布产物不得成为工作区。
- Owner/Operator、OAuth、密钥、工具证据和高危动作确认继续由代码强制。
- 现有 contracts、core、runtime、Web 和 .NET 测试必须持续通过。

## 2. 路径和数据分层

### 2.1 项目注册表

平面路径列表升级为结构化项目记录：

```ts
export interface RegisteredProject {
  id: string;
  displayName: string;
  type: 'unity' | 'node' | 'dotnet' | 'generic';
  workspaceRoot: string;
  accessMode: 'read_only' | 'read_write';
  unityProjectRoot?: string;
  mcpProfileIds?: string[];
  enabled: boolean;
}
```

当前项目建议记录：

| 项目 | Workspace/Git 根 | Unity 工程根 |
|---|---|---|
| ST4 | `F:\unity\ST4` | `F:\unity\ST4\Game` |
| ST3 | `C:\unity\ST3` | `C:\unity\ST3\Game` |
| ST3 Master | `F:\unity\ST3_master` | `F:\unity\ST3_master\Game` |
| codex-im-suite | `C:\Users\admin\Documents\New project\codex-im-suite` | 无 |

禁止注册：

- `C:\Users\admin\.codex`
- `C:\Users\admin\.claude-to-im`
- `E:\cli-md`
- 整个 `C:\unity` 或 `F:\unity`
- `release`、日志、上传缓存和临时产物目录

### 2.2 会话 Scratch

通用聊天不再默认绑定真实 Unity 仓库，运行时为每个会话/回合生成：

```text
<CTI_HOME>/runtime/workspaces/<sessionId>/<turnId>/
```

项目专用会话继续绑定一个注册项目。其他注册项目只有被当前消息明确引用时才临时挂载。

### 2.3 输入、产物和长期事实

```text
<CTI_HOME>/runtime/uploads/<sessionId>/<turnId>/     入站图片、文件、卡片资源
<CTI_HOME>/runtime/artifacts/<sessionId>/<turnId>/   模型和工具生成物
<CTI_HOME>/runtime/logs/                              日志和诊断
E:\cli-md/                                           Agent Home 与长期记忆
<project>/                                            只保存用户明确要求进入项目的源码和资产
```

默认生成路径禁止使用 `process.cwd()`。产物只有经过显式“提升到项目”动作，才能复制或写入注册项目。

### 已确认的候选

| 路径 | 当前事实 | 默认处置 |
|---|---|---|
| `C:\unity\ST3\.codepilot-uploads` | 218 文件，约 81.05 MB，最后写入 2026-07-14 | 备份清单后清理，属于旧聊天缓存 |
| `C:\Users\admin\.claude-to-im\runtime\uploads` | 2091 文件，约 2.36 MB，含真实缓存和测试夹具 | 按引用、时间和类型分层清理 |
| `C:\unity\ST3\captures` | 1 个截图 | 人工确认，不自动删 |
| `C:\unity\ST3\cti_artifacts` | 2 个产物 | 人工确认或迁移到 artifact store |
| `C:\unity\ST3\lark-im-resources` | 3 个下载资源 | 人工确认后迁移或删除 |
| `F:\unity\ST3_master\codex-output` | Skill 包与输出 | 人工确认，不自动删 |
| `Game/Assets/Screenshots` | Unity 会自动导入的项目资产 | 禁止自动清理 |

清理必须遵守：

1. 先生成 UTF-8 JSON/Markdown 清单，记录绝对路径、大小、修改时间、Hash、Git 状态和分类。
2. 默认 dry-run。
3. Bridge、watcher 和相关工具停止后才允许清理运行态缓存。
4. 未知文件、Unity `Assets`、用户输出、Skill 包、文档和项目源码默认保留。
5. 删除前将候选移动到工作区外的隔离备份目录，不直接永久删除。
6. 清理后重新运行 Git 状态、Bridge 状态和引用完整性检查。
7. Runtime uploads/artifacts 增加 TTL、容量上限和按 session/turn 的引用计数。

## 6. 总体验收标准

- 任意普通聊天回合结束后，当前项目 Git 状态不因附件、测试夹具或默认产物发生变化。
- 所有临时路径都有 session/turn 归属、来源、Hash、TTL 和容量限制。
- 项目注册根不自动进入 Prompt 或工具根。
- `.codex`、`.claude-to-im`、Agent Home、release、logs 和 uploads 永不成为主工作区。
- 多 Agent 可以分别修改 contracts、core 子域、runtime 子域、panel feature 和 skills，而不集中冲突巨型文件。
- 跨包依赖只通过稳定 exports/contracts。
- 面板只做控制、观察、配置、审批和手动兜底。
- Skill 只做可复用工作流和领域知识，不取代代码级安全门禁。
- 清理动作可 dry-run、可审计、可恢复，不删除未知 Unity 资产或用户产物。
- 所有现有测试、Manifest 校验、架构检查和真实 live 验收通过。
